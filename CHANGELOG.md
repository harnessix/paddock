# Changelog

## Unreleased

## 0.2.2

- Security: a host device is marked everywhere. The card says "allow the device `notes` for this sandbox: it runs ON THE HOST as you" with the command and `cwd`, and never skips, whatever `mode` says. The catalog has `"run": "host"` and a `request` text that begins with "Runs on the host as you, with your home, your keys and your network." `paddock device ls` prints `HOST`, `paddock doctor` lists the host devices under "devices that run on the host as you" with their commands, `paddock ps` shows `device notes (host, running 3m, pid N)` under the sandbox (`--json`: `devices`), and every audit line has `"run": "host"`.
- Security: `grant = ["remote:HOST"]` (the address, or a name that resolves to it) or `remote:any` is the only grant that reaches a remote caller; `all`, a table without a grant key, `--device`, a pasture or a project never do, and a `remote:` grant never grants to a sandbox of this host. A device without it answers `status: disabled` with the grant to add. The ssh transport runs `ssh` on the host as you, so the forward is marked like a host device: the card says "it connects to HOST with your ssh as you" and shows every session, `mode = "allow"` is a parse error for an ssh target, and the catalog text begins with "Connects to HOST with your ssh as you."
- Security: policy.rs keeps refusing a device mount of `/`, the home (unless `home` says so), a protected folder or another run's folders; a single read-only file of `ro` under a protected folder passes, because the user named it on the host. `deliver` credentials reach a device as a file only; `gateway` and `intercept` are refused with the fix.
- Security: a shared instance serves the device table that it read at its start. It refuses a run whose view of that table differs. The request fails with `EIO`. The catalog says the device was reconfigured and names `paddock device restart NAME`. So an edit of the user configuration is never served half old and half new.
- Security: on macOS, the guest agent refuses `clock.set`, `configure`, `data.prepare` and `shutdown` from the moment that it answers `app.launch`. Before, a request with the guest password that came right after the launch passed the guard until the next window poll. A second `app.launch` in that moment started a second app.
- Security: paddock kv has named namespaces. `[kv.namespaces.NAME]` of the user configuration names the projects (`projects`) and optionally the harnesses (`harnesses`) that share the scope `ns:NAME`. Other sandboxes cannot read or write it. Use a namespace instead of the `user` scope when only a few projects share state, for example compile slots.
- Security: in a sandbox, paddock chooses the session of a `mac` request before it asks, and the card and the session grant name that session and its pid. The card shows every typed character (a Return as ⏎), a request types at most 1000 characters, and the card says what a grant reaches, also the host clipboard in the guest. In app scope the guest agent refuses the known shortcuts of the system by any name of their key (not a shortcut that the user changed or added), refuses the Help menu shortcut by the character of its key on the guest's layout, clicks on the menu bar, drags and double or triple clicks with the right button or ctrl, and every input and every press but escape while a menu is open. It stops keys and text when the app leaves the front or a menu opens. If a drag opens a menu, the guest sends escape before the let-go. It looks for the menu for 0.5 s after the press and again before the let-go. The guest reads the keyboard layout on the main thread. A failed post releases the keys and the mouse button that it held down. A guest that never answers or streams frames cannot hold a host call past its time or fill its memory, and text from the guest loses its control characters before it reaches a terminal.
- Security: On macOS, the gateway signing key moves to the temporary folder of the user (`DARWIN_USER_TEMP_DIR`), which macOS empties at each restart. paddock removes the old key in `~/.local/state/paddock/run`.
- Security: `paddock app run` refuses an App Store app in the macOS guest with one line. The guest has no Apple ID. The line says to install the vendor's download instead.
- Security: if the host bundle carried the user's approval, the guest removes the quarantine attribute from the copy. Otherwise the attribute stays.
- Security: the `guest-files` port of the macOS guest takes 16 MiB per transfer, 64 transfers per minute, and closes a transfer idle for 10 s.
- Security: in modes `api` and `allowlist` the host list decides before any firewall rule, so a forged guest identity cannot pass it; a rule that allows every host needs `--yes-all-hosts`.
- Security: the session helper accepts one guest control connection per session; a second connection on the control port is refused until the first ends.
- Security: Each file of a release has a GitHub build provenance attestation. `gh attestation verify FILE --repo harnessix/paddock` shows that the release workflow of this repository built the file from the commit of the tag. README.md, Install, has the steps. The release workflow checks that the tag did not move before it makes the attestations, and it runs every action from outside this repository at a pinned commit.
- New: network mode `allowlist` works on macOS. Terminal runs and app mode use Seatbelt with paddock's proxy, which lets through only the hosts of the list (the same list that srt gets on Linux). `--backend auto` picks Seatbelt for it. A refused host goes into the audit log and the boundary log, with the reason `network mode allowlist: ...`.
- New: At the start of `paddock run`, an automatic cleanup runs in the background, at most once an hour. It removes merged worktrees without uncommitted changes, also after a cherry-pick or a rebase. It deletes the build output of worktrees that were not used for 2 days. It removes old snapshots. It never removes a sandbox home, because a home holds your conversations with the harness. `[storage] auto_gc = false` turns it off.
- New: When a `--worktree` run or a spawned worker ends without a commit and without a change, paddock removes its worktree and its branch.
- New: Below a hard floor of free space (15 GB or 5%), paddock runs the cleanup and then refuses to start a sandbox. Below a soft floor (50 GB or 10%), it warns. While sandboxes run, it sends a notification at the hard floor. `paddock doctor` shows the free space, the floors and the last cleanup.
- New: Worktree runs and workers of a Rust project build outside the worktree. Each one gets a copy-on-write copy of the newest build of the same repository. `[setup] shared_build_cache = false` in `paddock.toml` turns it off for a project.
- New: `paddock board` shows every project, ticket and agent run at a glance, the most urgent first, with the waiting approvals and the held compile slots at the top. `--json` prints the data for the Omarchy panel (version 1), and `--watch` draws it again on each change. `paddock help board-guide` explains the states.
- New: paddock records the prompt file of `paddock run --detach --prompt-file` and of `paddock-host spawn --prompt-file`, so the board maps each run to its ticket in `.paddock/tickets/`.
- New: each project of `paddock board --json` has the field `loft` when its loft has a notes folder, with or without a `.paddock` link in the project. The field is the absolute folder `<data>/loft/KEY/tree/.paddock`, so the Omarchy panel can open a ticket file that is only in the loft. A path with control or invisible characters gives no field and a warning. The contract stays version 1.
- New: A build from a git checkout that is not a clean checkout of a release tag is a development build. `paddock --version` then prints `-dev`, the commit and a dirty mark, for example `paddock 0.2.1-dev (commit 1a2b3c4, dirty)`. A release prints only `paddock 0.2.1`. `paddock doctor --report` has a line `Build:` with `release` or `development build` and the full commit.
- New: Codex runs get paddock's mail hooks. With unread mail, the Stop hook keeps the turn going with the messages, and an interrupt comes after the next tool call, as in Claude Code.
- New: a detached agent's done status produces a mailbox event and ends the run after `[mail] end_after_done` (default `2m`), unless a view is attached or new mail arrives.
- New: `[devices.NAME]` tables take `shape` (`exec`, `serve`), `run` (`sandbox`, `host`, `remote`), `scope`, `start`, `stream`, `grant`, `mode`, `max_request`, `max_response`, `concurrency`, `idle`, `ready` and a `[devices.NAME.sandbox]` profile (`network`, `allow`, `connect`, `ro`, `rw`, `home`, `env`, `env_pass`, `credentials`, `caller`, `mem`, `cpus`). Every wrong value is a parse error that names the table, the key, the allowed values and the fix; an unknown key is an error.
- New: a sandbox sees a device when a grant covers it: `paddock run HARNESS --device NAME`, `paddock-host spawn --device NAME` from a sandbox that has it (never more than its parent), `[pastures.NAME] devices = [...]`, `grant = ["pasture:NAME", "project:PATH", "harness:NAME", "all"]` in the table, or no `grant` key at all (every sandbox, as before). A project `paddock.toml` can ask with `[devices] use = [...]` under the one-time approval; it never turns a device on. A device that no grant covers answers "disabled" and names the missing grant.
- New: `paddock device ls`, `show`, `add` and `example`. `paddock devices` stays as an alias; `budget` and `ledger` moved under `paddock device`.
- New: `paddock doctor` prints a line per device table with an old spelling (`kind = "command"`, `max_body`) and the new one, per device that runs on the host, per device without a grant whose sandbox reaches something, and per `project:` grant whose folder does not exist.
- New: the device-facing contract. A device program is an `exec` command (the request on its standard input, the response on its standard output, exit 65 rejected, 75 still waiting, 77 declined) or a `serve` program that answers HTTP/1.1 on the Unix socket `$PADDOCK_DEVICE_SOCKET` (`POST /v1/call` with the `Paddock-*` headers of the caller, `GET /v1/health`, `GET /v1/catalog`, `Paddock-Cost`, `Paddock-Protocol-Min`). `paddock help device-guide` has the tables.
- New: `paddock device-serve` (hidden), the supervisor that puts a program behind such a socket: it forks an `exec` program per request in an empty working folder with the caller in `PADDOCK_*` variables, kills the process group at `timeout` and on cancel, caps the output at `max_response`, and proxies to a `serve` program after its health answered, with a restart backoff of 1, 2 and 4 seconds and `failed` after three exits within a minute. `--connect PORT:SOCKET` relays `127.0.0.1:PORT` to a socket of the broker. The log has one line per request and the program's stderr, never a body, 10 MiB with one rotation. It ends with its parent and on SIGTERM.
- New: one client in the broker speaks to every device program (`devices::program`), with the status mapping of the contract, chunked bodies, the `Paddock-Cost` header and two enforcers of `timeout` and `max_response`. `devices::outproc::OutOfProcess` runs the gate, the budget, the `concurrency` slots and the audit for such a device; the audit line has `shape`, `instance` and `http`. The device sandbox and the host mode plug into it.
- New: `run = "host"` runs a device program on the host as you: an `exec` command per request in `cwd` (default: your home) with your whole environment and the fixed values of `env`, or a `serve` program once per run on a socket of the run. The supervisor is `paddock device-serve --host`, started at the first request and ended with the run, so the envelope, the exit mapping, `timeout`, the kill of the process group, `concurrency` and the log are the ones of every device program. A missing `cwd` answers `status: error` with `message: cwd ~/notes does not exist`. A command that is not on your PATH answers `message: NAME is not on the PATH of the host`.
- New: `paddock device check NAME` for a host device prints the warning line first, then starts the supervisor on the host, waits for its health, prints the start time and stops it. `paddock device stop|restart NAME --sandbox ID` reach a host instance as they reach a device sandbox.
- New: a host instance writes the same state file as a device sandbox, `~/.local/state/paddock/devices/instances/NAME/SANDBOX.json`, with `run: host`, so `paddock ps`, `paddock device ls` and the stale cleanup treat both alike.
- New: the device sandbox on macOS. A device table with `run = "sandbox"` runs its program under Seatbelt (`sandbox-exec`) with a profile built from `[devices.NAME.sandbox]`: the system read-only, a private home and `TMPDIR`, `ro` and `rw` at their own paths, the real home denied unless `home` says else, no IP network, or the `connect` ports on localhost only. `caller = ["project:ro"]` gives the caller's project at its host path (`PADDOCK_CALLER_MOUNT`), a secret file is a FIFO in the instance folder, and the ssh agent of a credential is a socket the sandbox can only connect to. `paddock ps`, `paddock device check|logs|stop|restart|stats` and `paddock device ls` work as on Linux; the state file says `"backend": "seatbelt"`, and the catalog entry of a sandbox or host device says `"platform"` (`macos` or `linux`).
- New: `run = "remote"` forwards each request of a device to a paddock on another machine, which runs the device there in its own device sandbox, with its own table, card, audit line and log. The table names `target = "ssh://HOST"` or `"unix:/PATH"` and `device = "NAME"`, the device on the other side; no command, no shape, no sandbox table here. The local `timeout` is the whole round trip, a cancel closes the transport and the program on the other side is killed, the errors of the other side arrive unchanged (`EINVAL`, `EACCES`, `ETIME`, `ETIMEDOUT`), a transport that fails is `EIO` with the reason in `last_error` of `.catalog`, and `stream = true` brings the output as it comes.
- New: `paddock device serve-remote [--socket PATH]` serves the devices of this machine to another paddock, on the standard input and output (one request per process, as `ssh HOST paddock device serve-remote` runs it) or on a Unix socket in a 0700 folder. The identity of a remote caller is the transport: the ssh client address of `SSH_CONNECTION`, or `local` for a socket. What the caller says about itself is text for the card ("allow the device `build` for a remote caller from 192.168.1.5 (sandbox 3f2a on linuxbox)") and the audit line (`remote_caller`, `remote_host`, `remote_chain`). A remote caller gets no built-in device and no secret file. "Allow for this session" holds for 8 hours per peer and device in `~/.local/state/paddock/devices/remote-sessions.json`; `--forget` removes them.
- New: `paddock device check NAME` for a remote device reaches the other side as you and prints the entry of the device there. `paddock device add NAME --run remote --target T --device D` writes the table. `paddock doctor` lists remote devices under "devices of another paddock". `paddock device ls` and `show` print `remote` and the target.
- New: the device sandbox on Linux. A device table with `run = "sandbox"` runs its program in a bubblewrap sandbox of its own, built from `[devices.NAME.sandbox]`: the system read-only, an empty home, its own `/tmp` (`tmp = "4G"`), no network, widened by `network`, `connect`, `ro`, `rw`, `home`, `env`, `env_pass`, `credentials` (an ssh agent per instance, secret FIFOs), `caller = ["project:ro"]`, `mem` and `cpus`. One instance per agent sandbox, started at the first request or `with-sandbox`, in a systemd scope `paddock-dev-<sandbox>-<name>`, ended with the run, with `paddock stop`, and when the paddock process dies.
- New: `connect = ["2222:mac.local:22"]` on the host side: the broker resolves and connects from the host, one connection at a time, with one audit line per connection (host, port, bytes, duration, `lan`), never content.
- New: `paddock device check NAME [--send REQUEST]`, `logs NAME [--sandbox ID] [-f]`, `stop|restart NAME [--sandbox ID | --all]` and `stats NAME [--since 7d]`. `paddock ps` shows `device NAME (sandbox, running 3m, pid N)` under a sandbox, `--json` lists them under `devices`. `paddock device ls` shows the running instances. `paddock freeze` freezes the device scopes of a sandbox with it.
- New: a state file per instance (`<state>/devices/instances/NAME/ID.json`, written whole) and a log per instance (`<state>/devices/log/NAME/ID.log`, 10 MiB, one rotation). Stale files of a killed process go at the next start.
- New: `scope = "shared"` in a `[devices.NAME]` table runs one instance of the device per user. Every sandbox that has the grant uses that one instance. Use it for a program that is expensive to start, or that holds a warm state. The first broker that needs the device starts `paddock deviced NAME`. Every broker then connects to one socket in the runtime folder. The instance ends after its last run ended and `idle` seconds passed without a request.
- New: each run holds one open connection to the instance as its lease. A run that `kill -9` removes drops its lease at once. One broker that fails never takes the instance down.
- New: `paddock device install NAME` hands the socket of a shared device to the user manager. On Linux it writes two systemd user units. On macOS it writes a LaunchAgent with a `Sockets` entry. The first connection then starts the instance, and no broker starts it itself. `paddock device uninstall NAME` removes those files again.
- New: without an install, `systemd-run --user` starts the instance where a user manager runs. Without a user manager, the first run owns the instance. paddock then logs a notice that names that run.
- New: `paddock device stop NAME` ends the one shared instance of the user. `paddock device restart NAME` ends it so that the next one reads the table as it is now. With a user manager it also starts the new one at once. `paddock device logs NAME` prints its log.
- New: `paddock device ls` shows `shared, 3 users`. `paddock ps` shows the instance once, at the top, with its user count and its unit. `paddock device check NAME --hold SECONDS` keeps a device warm while you look at it.
- New: a device with `stream = true` answers as it goes. On Linux a read of `/dev/paddock/NAME` returns bytes as the program writes them, and the end of file comes when the program ends; a failure after the first byte fails the next read with `EIO`, never a silent truncation. `max_response` holds for the whole stream (`EMSGSIZE` at the byte that passes it), paddock keeps about 1 MiB of a stream in memory whatever its size, and closing the file ends the program within 300 ms. The catalog says that a stream is read once, in order.
- New: `paddock-host device NAME` prints a stream as it comes, in reads of 64 KiB, and exits with 7 after a failure that came after the first byte (75 when the device says still waiting after bytes), with a message that names how many bytes came first.
- New: the device socket of macOS carries a stream in chunks when the client asks for it with `"stream": true`: a 4-byte length and the bytes, a 0 chunk for a clean end, and a close without it for a failure after the first byte. An older client gets the response whole with `size`, and a newer client reads a `size` answer of an older server.
- New: `/dev/paddock` is an open device interface. A device is a program of yours in any language. You declare it once in `[devices.NAME]` of the user configuration and grant it by run, pasture, project or harness. It runs as an `exec` command per request, or as a `serve` program behind HTTP/1.1 on a Unix socket. It runs in a device sandbox of its own by default (`run = "sandbox"`), on the host as you (`run = "host"`, marked everywhere), or on another machine (`run = "remote"`). There is one instance per sandbox, or one per user (`scope = "shared"`). A device can stream. The fragments `devices-config`, `devices-contract`, `devices-sandbox`, `devices-stream`, `devices-host`, `devices-macos`, `devices-shared` and `devices-remote` have the details of each part. This note is the summary of the series, with the worked example and the numbers.
- New: the worked example `mac`. `paddock device add --example mac --host mac.local --user me` writes `[credentials.mac-ssh]`, `[devices.mac]` and `[devices.mac.sandbox]` into the user configuration and `~/.config/paddock/devices/mac/build.sh`, then prints the Mac steps. The steps are the key in your agent, `authorized_keys` on the Mac, the host key line that `ssh-keyscan` found for `~/.ssh/known_hosts_mac`, and rust on the Mac. The last step is the `devices = ["mac"]` line of the pasture, which the command never writes. Workers in the pasture run `printf test | paddock-host device mac -` and see the cargo output of the Mac stream. The device reaches one host and port through the broker, and signs with the key through a filtering agent. It checks the host key under the Mac's name (`HostKeyAlias`) although it connects to `127.0.0.1:2222`. It reads the caller's worktree read-only. A wrong request answers exit 65 of the script, which is `EINVAL` and exit 8 of `paddock-host device`. `paddock help device-guide` follows the same steps. `tests/devices_mac_example.rs` runs it against a stand-in sshd on the loopback.
- New: `paddock doctor --escape --device NAME` runs an escape probe as the program of a device, in its device sandbox. It checks that the host's home and runtime folder are hidden, that the private key of a credential is absent, and that `~/.ssh` has only the files the table binds. It checks that the host loopback and the LAN are unreachable, that the caller's project is read-only, and that there is no `paddock-host`. The connect ports of the table must be reachable inside. The command prints one line per check. If one check failed, the exit code is 1.
- New: exclave GPU runs see sysfs read-only for NVIDIA discovery. Peer owners can add read-only paths for installed tools in `[exclave.serve]`.
- New: exclave peer owners can set private package mirrors and environment settings, a dedicated bounded cache volume for Python environments, and GPU access for explicit requests. The peer PATH includes local system tools.
- New: exclave sends plain folders without Git, follows their ignore files, and accepts an explicit project root with `--root`.
- New: Run project commands on a configured peer in an isolated exclave.
- New: `paddock gauge [FEATURE]` shows how far a Spec Kit feature is, from the history of `tasks.md` and not from what the agents say: the done tasks with and without evidence, the tasks discovered per day, the reopened tasks, the fails after done, the age of each open task, and the time that tasks sat almost done. It forecasts the P50 and P85 of the finish date and of the final task count with a seeded Monte Carlo, says "not converging" when new tasks arrive as fast as tasks finish, shows the trend of P85 and a burn-up chart with the scope line. `--json`, `--strict`, `--seed`, `--window` and `--at` change the output.
- New: a task counts as done with evidence only when its work is merged, its review passed or a gate passed for it. `paddock spec gate TASK GATE pass|fail|skip` records a gate result on the host. A gate that only skipped, or a worker report that says its tests skipped and names no passing run, does not count as done.
- New: `paddock spec appetite FEATURE VALUE` sets the time budget of a feature (for example `3d`). paddock sends an `appetite` event to the mailbox of the run at 50 %, 80 % and 100 % and at every 25 % after that, each one once. It never stops the work.
- New: inside the sandbox, `paddock-host gauge` gives a coordinator the same gauge, computed on the host.
- New: paddock keeps a log of the task states next to the task records, so a project without git gets a task history from its first run on.

A fork inside a turn is refused. Other versions and schemas are refused.
- New: (experimental) in horse mode, an agy child of `paddock-host spawn` runs with `--input-format stream-json --output-format stream-json`. paddock stops a running turn with SIGINT. A line that names another conversation ends the custody.
- New: (experimental) an interactive agy in horse mode gets queued entries through the pty relay. paddock adds the `PreInvocation` and `Stop` hooks to the sandbox copy of `.gemini/config/hooks.json`.

It writes a session or a fork back as a transcript in the shape of a native `/branch` fork. Other versions are refused. The hidden commands are `paddock horse ingest-claude` and `paddock horse project-claude`.

- New: (experimental) `paddock horse swap SESSION BRANCH` continues a Codex session at another branch under the same thread id, so the cached prefix up to the fork point stays warm. If a headless run holds the session, the swap waits for the end of the turn, or stops it with `--interrupt`. An interactive run refuses the swap until it ends. With no run, `--codex-home` names the rollout. A swap that loses cached tokens needs `--yes`, and the old head stays in the store.
- New: (experimental) `paddock horse fork SESSION --warm` opens a warm side branch of a held Codex session under the cache key of the parent. The parent waits until `paddock horse fork SIDE --close` or the end of the run. `paddock horse log` marks its nodes `live`, and no codec writes such a session back.
- New: (experimental) a sandbox in horse mode sees its own horse at `/dev/paddock/horse/self/`: the DNA, the lineage, and a folder for each session with its head, status, inbox and log. `paddock-host horse` reads the same data through the broker, also on macOS. If the sandbox has no `/dev/paddock/horse`, for example when FUSE is missing, the run says why.
- New: (experimental) a sandbox can change the context of its own horse with one command per write to `self/ctl`, or with `paddock-host horse ctl`: `fork`, `append`, `move`, `view` and `disconnect`. The answer of the last command is the content of `self/ctl`. `view SESSION NAME FILTER` makes the read-only file `self/views/NAME`, and `disconnect` ends the custody of a session at its next safe point.

A write without a grant, out of budget or on another horse fails with EACCES.
- New: (experimental) the prefix guard judges each `ctl` command first. An append at the end passes at once. A command that breaks the cached prefix shows an approval card with the lost tokens and the cost. A denied command fails with EPERM and changes nothing. Each command writes one line to the device ledger.
- New: (experimental) published DNA. A reference `registry://org/name@version`, `@latest` or `@sha256:HASH` resolves through a list of index folders to a signed manifest and its DNA. ## 0.1.7

A security release. Update from every earlier version. The docker and podman relay sent the user name and password of an `https://` host proxy in cleartext, and connected directly when it could not use the proxy URL. `recover --to` could be redirected into a protected folder, and a project file could reveal secrets to a flatpak app without approval.

- Security: if the host proxy URL uses a scheme that the docker and podman relay cannot use (for example `socks4://`), the relay refuses connections. Before, it connected directly, which changed the exit address that the user chose.
- Security: `paddock recover --to` walks to the target folder one folder at a time without following symlinks, checks where the opened folder really is, and creates the file in it. Before, it checked the path and then opened it again, so a sandbox that can write a folder on that path could swap it for a symlink in between and make paddock create a new file in a protected place such as `~/.ssh`.
- Security: a flatpak app start asks for approval of a project `paddock.toml` that widens access, the same as every other sandbox. Before, a project `[secrets] reveal` applied without approval and exposed a `.env` to a flatpak app.
- Security: the docker and podman egress proxy talks TLS to an `https://` host proxy. Before, it dropped the `https` scheme and sent the CONNECT request with the `Proxy-Authorization` header in plain TCP, so the proxy user name and password crossed the network in cleartext, even when the proxy then refused the request. Now the request and the credentials go only inside TLS, the proxy certificate must pass a check against the system trust store, and any TLS error fails the request instead of falling back to plain TCP. A remote `http://` or `socks5://` proxy with a user name in its URL still gets it in cleartext, as those protocols do, and paddock logs a warning. Reported in the Omarchy plugin marketplace review.

## 0.1.6

A security release. Update from every earlier version. It fixes four issues: the docker and podman proxy let IPv4-mapped addresses reach loopback and the LAN, a project's MCP config could mount other host folders, private request text was readable by other local users, and flatpak apps did not get the workspace protections. If you used `clipboard-write` with an older paddock, delete `~/.local/state/paddock/host-audit.jsonl`: older lines can hold clipboard text.

- Security: the docker and podman egress proxy treats IPv4-mapped (`::ffff:a.b.c.d`), IPv4-compatible and NAT64 (`64:ff9b::a.b.c.d`) IPv6 addresses as their IPv4 address in its loopback, host and LAN checks. Before, `::ffff:127.0.0.1` passed as "not loopback". The proxy also connects only to the addresses that it checked, so a second DNS lookup cannot point a name somewhere else. Reported in the Omarchy plugin marketplace review.

An MCP server in a project `.mcp.json` (or `opencode.json`, or the project `.gemini/settings.json`) whose command was a file in another repository's `node_modules` counted as a tool install, and paddock mounted that whole repository read-only at the next start, even if the server never ran. The sandbox was then able to read the files of that repository, such as its `.env`. Any other path, and any interpreter that a script header names, needs `[mcp] allow`, which a project `paddock.toml` sets only with your approval. `paddock mcp` lists the exact host paths that an approval mounts. For a package, paddock now mounts its `node_modules` folder, not the folder around it, and for a file in `~/.cargo/bin`, `~/go/bin`, `~/.bun/bin` or `~/.deno/bin` only that file. paddock hides credential-shaped files in every folder it mounts for an MCP server or for `[mounts]`, as it does in the project. The harness and MCP commands are no longer looked up in relative PATH entries, and paddock refuses a harness whose executable or interpreter is in a folder that the sandbox can write. `paddock doctor --escape` checks that a project `.mcp.json` that names another repository's package mounts nothing of it. Reported in the Omarchy plugin marketplace review.
- Security: other local users were able to read private request text. The host audit log kept up to 500 characters of each clipboard-write request, also for denied and timed-out requests, and a umask of 022 made the log readable by everyone. When the bar did not run, the approval notification passed the same text to `notify-send` as an argument, which every user can read in `/proc`. Now the audit log and the agent approver log keep no request text: only lengths for the clipboard, notifications and `gh` bodies, the program name for `exec`, and the scheme and host for URLs. Notifications go to the desktop bus directly, and `gh` reads the body text with `--body-file -` on its standard input. paddock creates its state, data, cache and runtime folders with mode 0700 and its files with mode 0600, and tightens older ones when it opens them. Lines that an older paddock wrote to `~/.local/state/paddock/host-audit.jsonl` and `approver-decisions.jsonl` can still hold clipboard text: delete those files to remove it. Keyring passwords and copied logins are private from the first byte. Reported in the Omarchy plugin marketplace review.
- Security: flatpak apps (`[app] flatpak = "ID"`) got their workspace folders without the git and secrets protection and without the path policy. The app was able to read a `.env` in a workspace folder, or change `.git/config` or add a hook that git then ran on the host, and a home folder or a folder such as `~/.ssh` was accepted as a workspace folder. It also got the whole host environment, with tokens and the control channels of the host session. Now each folder of a flatpak app goes through the same git and secrets detectors and the same policy as for other apps: `.git` is a mount point of its own, its `config`, `config.worktree`, `commondir`, `gitdir`, `objects/info/alternates` and `hooks` are read-only, `secrets.hide` folders are hidden, and protected paths are refused. flatpak cannot hide a single file, so paddock refuses to start a flatpak app when the secrets detector finds a file such as `.env` in its folders, and names the files. `unprotected_workspaces = true` in `[apps.NAME]` of `~/.config/paddock/config.toml` (never a project file) starts it anyway, with a warning on every start, in `paddock app list` and in the bar panel. `flatpak run` gets the same host environment filter as other sandboxes. Reported in the Omarchy plugin marketplace review.

- App worktrees: `paddock app run NAME --worktree`, or `[apps.NAME] worktree = true`, opens the first workspace folder in a new git worktree on the branch `paddock/<app>-<date>-<id>`. The folder dialog of a menu start offers it as the default for git repositories. When the app exits, paddock lists the worktree's commits and uncommitted changes.
- A sandbox started from a Claude app session no longer inherits the app's control channel (`CLAUDE_CODE_MESSAGING_TOKEN` and `CLAUDE_CODE_MESSAGING_SOCKET`).
- Network mode `egress` blocks the LAN by default: private, link-local and CGNAT ranges, on every backend. `[network] lan = true` allows it again. `paddock doctor --escape` checks it.
- Logging with levels. `-v` and `-q` change how much paddock prints, and `PADDOCK_LOG=debug` or `PADDOCK_LOG=broker=debug` sets the level for everything or for one part. The broker, the proxy, the login callback forwarder and the window border also write to the systemd journal: `journalctl -t paddock -p warning`.
- `paddock doctor --report` prints a diagnostic report for bug reports, without user names, paths, variable values or tokens.
- The bar plugin writes a warning to the shell log when it cannot read paddock's output. `PADDOCK_DEBUG=true` shows more.
- Sandbox artifacts: `paddock files` lists the files that a sandbox saved outside the project, in recovery folders such as `~/Desktop` and `~/Downloads`, and the project changes since the start. `paddock recover` copies them to the host without overwriting anything, and `paddock discard` deletes them. The Omarchy panel lists them and sends a notice when new ones appear. Set the folders in `[recovery]` of `~/.config/paddock/config.toml`.
- `paddock shims install` makes the sandbox the default: typing `claude`, `codex` and the other harness commands in bash or zsh starts them in a sandbox. `paddock shims remove` undoes it, and nothing breaks if paddock is removed first.
- A `paddock` agent skill for the host, next to `paddock-host`. Install both with `npx skills add harnessix/omarchy-paddock`.

## 0.1.0

The first public release.

- `paddock <harness>` runs a coding-agent harness with full auto-approval in a sandbox. The sandbox sees the project, a private home and nothing else of your files.
- Backends: bwrap (the default), docker, podman and srt.
- Network: outbound only. The bwrap backend uses pasta and blocks the addresses of the host. Containers reach the internet through a relay proxy only. Your system proxy and VPN routes stay as they are.
- Logins: isolated logins per harness, login callbacks through an approval, and a private keyring for harnesses that need one.
- Host requests: a sandbox can ask to open a link or use a host capability. You answer once, for the session, or deny, from an approval card or from `paddock approvals`.
- App mode: `paddock app run` runs a desktop app, such as VS Code, in a sandbox, with a marked window border.
- Displays for desktop projects: a private headless or window display, and `paddock-screenshot`.
- Launchers: `paddock launchers install` adds menu entries for the harnesses and apps that paddock finds.
- Omarchy bar plugin: lists sandboxes, starts new ones, shows recent requests and runs `paddock doctor`.
- `paddock doctor` and `paddock doctor --escape` test the setup and the sandbox limits.
