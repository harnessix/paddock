- New: a device with `stream = true` answers as it goes. On Linux a read of `/dev/paddock/NAME` returns bytes as the program writes them, and the end of file comes when the program ends; a failure after the first byte fails the next read with `EIO`, never a silent truncation. `max_response` holds for the whole stream (`EMSGSIZE` at the byte that passes it), paddock keeps about 1 MiB of a stream in memory whatever its size, and closing the file ends the program within 300 ms. The catalog says that a stream is read once, in order.
- New: `paddock-host device NAME` prints a stream as it comes, in reads of 64 KiB, and exits with 7 after a failure that came after the first byte (75 when the device says still waiting after bytes), with a message that names how many bytes came first.
- New: the device socket of macOS carries a stream in chunks when the client asks for it with `"stream": true`: a 4-byte length and the bytes, a 0 chunk for a clean end, and a close without it for a failure after the first byte. An older client gets the response whole with `size`, and a newer client reads a `size` answer of an older server.
- Changed: the `Device` trait gains `call_stream`; built-in devices and the `http` proxy keep answering whole. `OutOfProcess` streams the chunked response of `paddock device-serve --stream`.
- Changed: `stream = true` is available for `run = "sandbox"`: an `exec` table, a `kind = "command"` table of 0.2.1 and a `serve` table stream through the device sandbox, whose supervisor runs with `--stream`. The catalog entry of a streamed `exec` device says that the response is the raw standard output, read in order.
