- New: `/dev/paddock` is an open device interface. A device is a program of yours in any language. You declare it once in `[devices.NAME]` of the user configuration and grant it by run, pasture, project or harness. It runs as an `exec` command per request, or as a `serve` program behind HTTP/1.1 on a Unix socket. It runs in a device sandbox of its own by default (`run = "sandbox"`), on the host as you (`run = "host"`, marked everywhere), or on another machine (`run = "remote"`). There is one instance per sandbox, or one per user (`scope = "shared"`). A device can stream. The fragments `devices-config`, `devices-contract`, `devices-sandbox`, `devices-stream`, `devices-host`, `devices-macos`, `devices-shared` and `devices-remote` have the details of each part. This note is the summary of the series, with the worked example and the numbers.
- New: the worked example `mac`. `paddock device add --example mac --host mac.local --user me` writes `[credentials.mac-ssh]`, `[devices.mac]` and `[devices.mac.sandbox]` into the user configuration and `~/.config/paddock/devices/mac/build.sh`, then prints the Mac steps. The steps are the key in your agent, `authorized_keys` on the Mac, the host key line that `ssh-keyscan` found for `~/.ssh/known_hosts_mac`, and rust on the Mac. The last step is the `devices = ["mac"]` line of the pasture, which the command never writes. Workers in the pasture run `printf test | paddock-host device mac -` and see the cargo output of the Mac stream. The device reaches one host and port through the broker, and signs with the key through a filtering agent. It checks the host key under the Mac's name (`HostKeyAlias`) although it connects to `127.0.0.1:2222`. It reads the caller's worktree read-only. A wrong request answers exit 65 of the script, which is `EINVAL` and exit 8 of `paddock-host device`. `paddock help device-guide` follows the same steps. `tests/devices_mac_example.rs` runs it against a stand-in sshd on the loopback.
- New: `paddock doctor --escape --device NAME` runs an escape probe as the program of a device, in its device sandbox. It checks that the host's home and runtime folder are hidden, that the private key of a credential is absent, and that `~/.ssh` has only the files the table binds. It checks that the host loopback and the LAN are unreachable, that the caller's project is read-only, and that there is no `paddock-host`. The connect ports of the table must be reachable inside. The command prints one line per check. If one check failed, the exit code is 1.
- Changed: the device reference in `paddock help device-guide` is restructured. It covers what a device is, the built-ins, your own devices, the device sandbox, host devices, shared devices and remote devices. Then streaming, the worked example, the commands, the contract for device authors, migration from 0.2.1, and the limits. The "Your own devices" section of 0.2.1 is gone. Its tables are in the migration part. The paddock-host skill tells an agent how to use a device that builds elsewhere.
- Fix: if the program path of a `command` starts with `~/`, paddock expands it against your home when it reads the configuration. Before, the supervisor got the path as written and the request failed with "not found".
- Fix: a response of a device program whose first read held more than 16 KiB failed with `EIO` ("bad response"). The broker's client checked the size of the head before it parsed the head, and a fast program's body came in the same read. Now only a head longer than 16 KiB is refused. The bench found it: every collected response over 16 KiB that arrived at once was lost.
- Fix: a device sandbox started with the test launcher (`PADDOCK_TEST_DEVICE_LAUNCHER=thread`) now gets the `env` of its profile and the filtering ssh agent of its credentials, as the bubblewrap and Seatbelt launchers give them. `paddock device check` reads that variable too.
- The bench `tests/devices_bench.rs` (`cargo test --release --test devices_bench -- --ignored --nocapture`) prints the measures with their targets. Its contract layer (the supervisor as a plain process, the broker's client, no sandbox, no FUSE) measured this on a Linux host, release build:

  | measure | target | p50 | p95 | met |
  | :--- | :--- | ---: | ---: | :--- |
  | supervisor start (plain process, exec, health answered) | sandbox start: p50 under 250 ms, p95 under 500 ms | 51.3 ms | 51.7 ms | yes |
  | one exec request (cat) through the contract | p50 under 15 ms, overhead above a fork under 5 ms | 11.95 ms | 12.75 ms | p50 yes, overhead no |
  | a plain fork of cat, for the overhead | - | 1.23 ms | | - |
  | one serve request (python upper.py) | p50 under 4 ms | 0.44 ms | 0.75 ms | yes |
  | first byte of a stream, after the program wrote it | under 20 ms | 14.0 ms | 14.7 ms | yes |
  | 48 MiB response, collected (p95 is the slowest run) | over 200 MiB/s | 380 MiB/s | 248 MiB/s | yes |
  | 48 MiB response, streamed (p95 is the slowest run) | over 200 MiB/s, client memory under 16 MiB above idle | 672 MiB/s | 583 MiB/s | yes |
  | client RSS above idle while streaming | under 16 MiB | 0.0 MiB | | yes |
  | connect relay, one connection, 48 MiB there and back | over 100 MiB/s | 605 MiB/s | 356 MiB/s | yes |
  | idle supervisor: RSS, and wakeups per second | RSS under 10 MiB, 0 wakeups/s | 8.6 MiB | 5.0/s | RSS yes, wakeups no |
  | 16 parallel requests: wait above the longest single one | under 50 ms | 8.6 ms | 17.0 ms | yes |

  Two numbers are below target. The overhead of one `exec` request above a plain fork is about 11 ms, not 5: the supervisor makes a working folder per request, starts a thread for the standard input, and waits for the child with a poll instead of a wake-up. The p50 of 15 ms holds. An idle supervisor wakes five times a second, not zero: it checks its parent and its stop flag every 200 ms. Both are follow-ups in the supervisor (`devices/supervise`), not in the contract.

  Its full layer (a bubblewrap device sandbox, FUSE, the broker of a run) needs bubblewrap and FUSE; `sh packaging/macos/checks/devices-example.sh linux` measures it on a Linux host. The bench uses 48 MiB for the large responses, under the 64M cap.
